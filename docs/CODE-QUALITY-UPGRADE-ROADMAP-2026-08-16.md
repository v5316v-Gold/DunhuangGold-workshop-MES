## 三、详细改进任务清单

### 3.1 P0 任务（v1.1 → 8.0，1-2 个月）

#### 任务 P0-1：补充 API 集成测试
- **现状**：24 个后端测试，主要 CRUD；controllers 完全没测
- **目标**：controllers 27 端点每个 1-2 个测试，集成测试覆盖率 60%+
- **投入**：1 周
- **具体项**：
  - [ ] 编写 controllers/mes_api.py 集成测试（11 端点）
  - [ ] 编写 controllers/ehs_api.py 集成测试（10 端点）
  - [ ] 编写 controllers/device_api.py 集成测试（3 端点）
  - [ ] 编写 controllers/postprod_api.py 集成测试（4 端点）
  - [ ] 增加 `tests/test_controllers/__init__.py`
  - [ ] 补前端 → 后端集成测试（TransactionCase + mock user + 数据准备）
- **验收**：`pytest tests/` 全过，覆盖率 ≥ 60%，reports 行数 + 100+
- **预期提升**：测试 5.0 → 7.0

#### 任务 P0-2：补 CI/CD 实际工作流
- **现状**：README 有 CI badge，但 `.github/workflows/` 空
- **目标**：GitHub Actions 实际跑通（lint + test + build）
- **投入**：3 天
- **具体项**：
  - [ ] 创建 `.github/workflows/ci.yml`：
    - [ ] Python lint（ruff）
    - [ ] Odoo 测试（TransactionCase + pytest）
    - [ ] Manifest 验证（自定义）
    - [ ] XML 良构检查（xmllint）
    - [ ] Shell 脚本验证（`validate_dunhuanggold_workshop_mes.py`）
  - [ ] 创建 `.github/workflows/release.yml`：tag 触发，构建镜像 + 发版
  - [ ] 加 status badge 实际显示在 README
  - [ ] 加 branch protection（必须 CI 通过才允许 merge）
- **验收**：每次 push 触发 CI，5 分钟内出结果，PR 必须绿才能 merge
- **预期提升**：部署/DevOps 6.0 → 7.0

#### 任务 P0-3：补索引优化
- **现状**：金料/报工/盘点等大表未加 `index=True`
- **目标**：关键查询字段加索引
- **投入**：1 周
- **具体项**：
  - [ ] `gold.material.batch`：batch_no（已 index）、state、categ_id、product_id 加 index
  - [ ] `gold.workorder.report`：production_id、state、report_time、workstation_id 加 index
  - [ ] `gold.inventory.count`：state、counter_id、reviewer_id 加 index
  - [ ] `gold.environment.reading`：sensor_id、reading_time、state 加 index
  - [ ] `gold.hazardous.chemical`：stock_qty 加 check 约束
  - [ ] 用 `EXPLAIN ANALYZE` 验证大表查询
- **验收**：金料批次 10 万记录下查询 < 100ms
- **预期提升**：数据库/性能 7.0 → 7.5

#### 任务 P0-4：API 限流 + 审计
- **现状**：controllers 没限流，DoS 风险
- **目标**：所有 POST 端点加 rate limit（基于用户/IP）
- **投入**：2 天
- **具体项**：
  - [ ] 实现一个 `@rate_limit(calls=100, period=60)` 装饰器
  - [ ] 应用到 27 个 POST 端点
  - [ ] 加入 Redis 后端（用 Odoo 的 `ir.config_parameter` 或外部 Redis）
  - [ ] 429 Too Many Requests 响应
  - [ ] 审计日志（敏感操作写 `gold.audit.log`）
- **验收**：连续 200 次 POST/分钟触发 429
- **预期提升**：API 7.5 → 7.8，安全性 7.5 → 7.8

#### 任务 P0-5：OpenAPI 自动生成
- **现状**：27 端点手动维护在 docs/API.md
- **目标**：OpenAPI/Swagger 自动生成
- **投入**：1 周
- **具体项**：
  - [ ] 安装 `apispec` + `apispec-webframeworks` 库
  - [ ] 给每个 controller method 加 docstring 描述
  - [ ] 实现 `GET /api/v1/openapi.json` 端点
  - [ ] 集成 Swagger UI（`/api/v1/docs`）
  - [ ] 移除 docs/API.md 手动维护，改为自动生成
- **验收**：`/api/v1/openapi.json` 完整且实时更新
- **预期提升**：API 7.5 → 8.0，文档 8.5 → 9.0

## 六、风险与权衡

### 6.1 风险评估

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 测试编写遗漏边界 | 高 | 中 | 用 Hypothesis 属性测试 |
| TypeScript 迁移破坏现有页面 | 中 | 高 | 增量迁移 + 每页 E2E |
| HTTPS 证书过期 | 中 | 中 | certbot + cron + 监控 |
| AI 视觉训练数据不足 | 高 | 高 | 先用预训练模型 + 持续标注 |
| NGTC 链上链下数据一致 | 中 | 中 | 强一致协议 + 定时对账 |
| 用户对 React 重写抵触 | 中 | 中 | 保留 HTML 版本作为 fallback |
| 投入资源不足 | 高 | 高 | 优先 P0 + 2 周冲刺 |

### 6.2 权衡

- **测试 vs 速度**：先核心流程（报工/盘点/入库），后边缘（通知/UI）
- **TypeScript vs 简单**：TS 慢但长期维护好，纯 JS 快但易出错
- **React vs 纯 HTML**：React 功能强但重，纯 HTML 轻但难扩展
- **OpenAPI vs 维护**：自动生成省事但有学习成本，手动维护直观但易过期
- **K8s vs Docker**：K8s 强但复杂，Docker Swarm/Compose 简单但弱

### 6.3 不要做

- ❌ 不要为了追求"现代"而把稳定的纯 HTML 重写
- ❌ 不要一次性加 50% 性能（容易引入新 bug）
- ❌ 不要为不存在的需求做架构（YAGNI）
- ❌ 不要把所有测试都写成 unit test（要混合 E2E）
- ❌ 不要用 AI 生成的代码不 review

## 八、附录

### 8.1 评分方法论

每个维度评分基于：
- **代码质量**（命名/结构/可读性/最佳实践）
- **完整性**（是否有遗漏）
- **测试覆盖**（有/无/质量）
- **文档**（清晰/完整/最新）
- **可维护性**（未来改动成本）
- **性能**（实测基准）
- **安全**（合规/防护）

### 8.2 升级决策原则

- **优先级**：P0（必做）→ P1（应做）→ P2（可做）→ P3（远期）
- **投入产出比**：高 → 优先；低 → 推后
- **风险规避**：先做 P0 高 ROI 低风险；再做 P1
- **保持业务稳定**：测试 + 渐进式改造；不在大版本改动核心业务
